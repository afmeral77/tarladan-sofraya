The migrations create the identity and catalog foundation: profiles, businesses, producer/buyer/carrier role records, categories, products, inventory, harvest dates and role-specific business onboarding. All exposed public tables have RLS. Public catalogue reads require an active product and an approved, public producer; private business records are role- and owner-scoped. The signup trigger accepts only producer/carrier choices from user metadata; every other value falls back to buyer, so user metadata cannot grant admin. Producer verification/publication flags are not writable by producer sessions.

`complete_business_profile` is an authenticated `SECURITY INVOKER` RPC. It derives the role and identity from `auth.uid()`'s profile, writes only the matching role-specific profile, obeys existing table grants and RLS policies, and returns the business id. Buyer business type is enforced with a database check constraint even if a client attempts to bypass the form. The Supabase security advisor was clean after switching this function from its initial definer setting to invoker; the initial migration file is preserved as historical source, with a follow-up migration recording the change.

The Auth email provider and signup are enabled, and `mailer_autoconfirm=false` means a new user must confirm their address. Do not mark live email as tested: no real signup email was sent during implementation. Before inviting users, open Supabase Dashboard → Authentication → URL Configuration and set the correct `Site URL`, plus exact localhost, HTTPS Preview and final production callback URLs (`/auth/callback`). Configure and test a production SMTP provider; the app constructs its callback from the page's current origin and rejects external `next` redirects.

Apply migrations using the Supabase MCP migration operation and commit matching SQL files whose version prefixes match the remote migration history. The app uses `@supabase/ssr` browser/SSR clients and a root Next.js `proxy.ts` session refresher. `lib/supabase/config.ts` contains this project's public URL and publishable key as defaults so managed Preview/build work without uncommitted files. These are public by design; RLS protects private data. Environment values can override the defaults. Never put a Supabase secret/service-role key in a `NEXT_PUBLIC_*` variable or browser bundle.

Local development may use a root `.env.local` (ignored by Git); `.env.example` documents optional overrides only. Vercel is not connected yet, so production environment configuration can override the public defaults when that account is authorized. The first migrations deliberately do not add order, payment, subscription, delivery or audit tables; those workflows need their own reviewed migrations and policies.
